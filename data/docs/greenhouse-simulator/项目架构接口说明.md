## 1. 总体架构设计

### 1.1 设计原则

| 原则 | 说明 |
|------|------|
| **零侵入** | 不修改 Java 后端和 nanobot 上游代码，通过 HTTP/MCP/MQTT 协议集成 |
| **单一职责** | 每个服务只做一件事：Gateway = 鉴权网关，MCP = 工具层，Bridge = 传感器监听 |
| **幂等安全** | 所有读操作天然幂等；写操作通过 token-gated 二次确认保证安全 |
| **可观测** | 结构化日志 (loguru)，健康检查端点，WebSocket 在线用户统计 |
| **容错降级** | 每个环节独立失败，不级联崩溃；AI 分析失败时返回静态兜底消息 |

### 1.2 技术栈

| 组件 | 技术选型 | 版本 | 说明 |
|------|---------|------|------|
| Web 框架 | FastAPI | ≥0.120.0 | ASGI, 自动 OpenAPI 文档 |
| HTTP 客户端 | httpx | ≥0.28.0 | 异步, 支持 SSE 流式读取 |
| MCP 框架 | FastMCP | ≥1.26.0 | MCP 协议 Python SDK |
| 鉴权 | PyJWT | ≥2.10.0 | JWT 解码（不验证签名） |
| 缓存 | redis (aioredis) | ≥5.2.0 | 异步 Redis 客户端 |
| 定时任务 | APScheduler | ≥3.11.0 | cron/interval/date 触发 |
| MQTT | paho-mqtt | ≥2.1.0 | MQTT v2 客户端 |
| 图数据库 | neo4j | ≥5.26.0 | 可选, 知识图谱后端 |
| 日志 | loguru | ≥0.7.0 | 结构化日志 |
| 数据校验 | pydantic | ≥2.12.0 | 参数验证 |

### 1.4 技术选型理由

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 语言 Python 3.11+ | 统一胶水层语言 | 三个服务共享 httpx/loguru/pydantic，降低维护成本 |
| FastAPI (Gateway) | 替代 Flask/Django | 原生 async/await, 自动 OpenAPI, WebSocket 支持 |
| FastMCP (MCP Server) | 官方 MCP SDK | 标准 MCP 协议, 工具注册简单, 自动 SSE transport |
| paho-mqtt (Bridge) | MQTT v2 API | 成熟稳定, 支持 QoS 1, 后台线程运行 |
| PyJWT 不验签 | 兼容 Java JJWT | Java/Python HMAC-SHA512 签名不兼容, 改用 Redis 查找验证 |
| httpx 替代 requests | 全异步 | SSE 流式读取, 异步并发, 与 FastAPI 生态一致 |

### 2.2 核心模块详解

#### 2.2.1 `auth.py` — 鉴权模块

**设计决策**: 不验证 JWT HMAC-SHA512 签名。原因：Java JJWT 和 Python PyJWT 即使使用相同的密钥，HMAC-SHA512 签名的字节表示也不同。改为从 JWT 中提取 `login_user_key` (UUID)，在 Redis 中查找 `login_tokens:{uuid}` 验证 token 有效性。此方式与 Java 后端的验证逻辑等价，且支持即时踢人下线。

```
┌─────────────────────────────────────────────────────┐
│                   验证流程                            │
│                                                     │
│  JWT Token ──→ Decode (不验签) ──→ 提取 login_user_key │
│                                       │              │
│                                       ▼              │
│                              Redis GET              │
│                     login_tokens:{uuid}              │
│                                       │              │
│                              ┌────────┴────────┐    │
│                              │ 找到 → 解析用户   │    │
│                              │ 未找到 → 401     │    │
│                              └─────────────────┘    │
│                                       │              │
│                                       ▼              │
│                              UserIdentity           │
│                       {user_id, username,           │
│                        dept_id, permissions}        │
└─────────────────────────────────────────────────────┘
```

**Redis 数据格式**: 值为 Java fastjson 序列化的 `LoginUser` 对象。解析时需处理：
- `@type` 元数据字段（需移除）
- `123L` 长整型后缀（需转换）
- `Set[...]` 集合类型（需转为数组）
- 尾部逗号（需移除）

#### 2.2.2 `chat.py` — 聊天代理

**SSE 流式路径** (`stream_chat`):
1. 将用户 JWT 存入 Redis `mcp_jwt:{session_id}` (30min TTL)，供 MCP Server 读取
2. 在用户消息前注入系统身份前缀: `[System: 当前用户: {username} | 部门ID: {dept_id}]`
3. POST 到 nanobot `/v1/chat/completions` (stream=true)
4. 解析 SSE 行，提取 OpenAI 兼容格式的 `delta.content`
5. 逐块 yield `data: {"content": "..."}` SSE 事件
6. 结束时发送 `data: {"done": true, "session_id": "..."}`

**非流式路径** (`inject_message`): 用于 Scheduler 和 MQTT Bridge 的后台静默分析。相同请求结构但 `stream: false`，返回完整响应文本。

#### 2.2.3 `scheduler.py` — 定时任务调度器

**触发类型**:

| 类型 | 配置字段 | APScheduler Trigger | 示例 |
|------|---------|---------------------|------|
| `cron` | `cron_expr`, `tz` | `CronTrigger` | `"0 8 * * *"` (每天8点) |
| `every` | `every_seconds` | `IntervalTrigger` | `3600` (每小时) |
| `at` | `at_iso` | `DateTrigger` | `"2026-07-10T09:00:00"` (一次性) |

**持久化**: 任务以 JSON 格式存储在 `TASK_STORE_PATH`，支持原子写入（先写 `.tmp` 再 `os.replace`）。启动时自动恢复所有已启用的任务。

**任务生命周期**:
```
创建 → 启用(默认) → 触发 → 更新 last_run_at/run_count → 持久化
                ↕
              禁用(暂停) → 重新启用
                ↓
              删除(移除 APScheduler Job + 持久化)
```

#### 2.2.4 `ws_manager.py` — WebSocket 连接池

**核心设计**:
- 支持每用户多设备连接（一个 user_id 可以有多个 WebSocket 连接）
- `asyncio.Lock` 保证并发安全
- 30 秒心跳循环：发送 `{"event": "ping"}`，失败的连接被清理
- 推送操作静默处理断开连接（依赖心跳清理）

**连接池结构**:
```python
_clients: dict[str, list[WSClient]]
# WSClient = {user_id, ws, connected_at}

# 同一用户的多个设备:
"user:1001": [
    WSClient(user_id=1001, ws=<WebSocket>, connected_at=...),
    WSClient(user_id=1001, ws=<WebSocket>, connected_at=...),  # 第二个设备
]
```

### 3.2 核心模块详解

#### 3.2.1 `validators.py` — 6 层参数校验引擎

**设计理念**: 所有 LLM 传入的参数都视为不可信输入，逐层校验。

```
┌─────────────────────────────────────────────────┐
│              6 层校验管道                         │
│                                                 │
│  Layer 1: 类型检查                               │
│    └─ 参数是否为期望类型 (str/int/float)          │
│                                                 │
│  Layer 2: 注入检测                               │
│    └─ 正则匹配 8 种 prompt injection 模式         │
│    └─ 匹配 → HardBlockError (不可恢复)            │
│                                                 │
│  Layer 3: ID 格式校验                            │
│    └─ GH + 3+ 位数字 / D + 3+ 位数字             │
│                                                 │
│  Layer 4: 物理范围校验                            │
│    └─ 温度 -50~80℃, 湿度 0~100%, 光照 0~200klux │
│                                                 │
│  Layer 5: 实体存在性校验                          │
│    └─ 调用后端 API 验证大棚/设备是否存在           │
│                                                 │
│  Layer 6: Token 网关 (仅写操作)                   │
│    └─ 二次确认: 首次返回 token, 再次携带 token 生效 │
│                                                 │
│  ValidationError ← 可恢复 (LLM 可重试)           │
│  HardBlockError  ← 不可恢复 (安全拦截)            │
└─────────────────────────────────────────────────┘
```

**注入检测模式** (8 种):

```python
r"ignore\s+(all\s+)?(the\s+)?(previous|above|prior|current)\s+instructions?"
r"forget\s+.*instructions?"
r"you are now\s+(a\s+)?(different|new)"
r"pretend\s+(you are|to be)"
r"act as\s+(if\s+)?(you are|a different)"
r"system_prompt:"
r"<\|im_start\|>"
r"<\|im_end\|>"
```

**物理范围常量** (`SENSOR_BOUNDS`):

| 传感器类型 | 最小值 | 最大值 | 单位 |
|-----------|--------|--------|------|
| temperature | -50 | 80 | ℃ |
| humidity | 0 | 100 | % |
| light | 0 | 200000 | lux |
| co2 | 0 | 10000 | ppm |
| wind_speed | 0 | 60 | m/s |
| soil_moisture | 0 | 100 | % |
| ph | 0 | 14 | — |
| soil_temperature | -50 | 80 | ℃ |
| battery | 0 | 100 | % |

**Token-Gated 写确认机制**:

```
LLM 第一次调用 set_threshold(...)
    │
    ▼
validators 校验参数 → 通过
    │
    ▼
返回: "⚠️ 确认操作：设置阈值... 请携带以下 token 重新调用:
       confirmation_token: a1b2c3d4e5f6"
    │
    │  (token 存入内存，5 分钟有效，单次使用)
    │
    ▼
LLM 第二次调用 set_threshold(..., confirmation_token="a1b2c3d4e5f6")
    │
    ▼
validators 校验 token → 匹配 → 执行操作 → token 作废
```

#### 3.2.2 `dongzao_client.py` — Java 后端客户端

**架构**: 异步 HTTP 客户端，封装所有 Java 后端 REST API。

```
┌────────────────────────────────────────────────┐
│              DongzaoClient                      │

│       │                                        │
│       ├── _get(path, params)                   │
```

### 4.2 核心设计

**单文件架构** — 整个服务在 `bridge.py` 一个文件中实现。

**双线程模型**:
```
┌─────────────────────────────────────────────┐
│  paho 后台线程                               │
│  ┌───────────────────────────────┐          │
│  │ MQTT Client.loop_start()      │          │
│  │  └── on_message() 回调        │          │
│  │      └── run_coroutine_threadsafe()      │
│  └───────────────┬───────────────┘          │
│                  │ 跨线程调度                 │
│  ┌───────────────▼───────────────┐          │
│  │  asyncio 主事件循环            │          │
│  │  └── _handle_alert()          │          │
│  │      ├── inject_alert_analysis()  ← nanobot │
│  │      └── push_to_gateway()        ← gateway │
│  └───────────────────────────────┘          │
└─────────────────────────────────────────────┘
```

### 4.3 告警处理流程

```
MQTT 消息到达 (topic: dongzao/greenhouse/{id}/{sensor_type})
    │
    ▼
on_message() [paho 线程]
    ├── 解析 topic → greenhouse_id, sensor_type
    ├── 解析 payload → {value, unit, status, ...}
    ├── 检查 status == "critical" 或 "warning"
    │   └── "normal" → 静默丢弃
    ├── 去重检查: DedupCache.should_trigger("{gh_id}:{sensor_type}")
    │   └── 5 分钟内重复 → 静默丢弃
    └── run_coroutine_threadsafe(_handle_alert())
            │
            ▼ [asyncio 事件循环]
        _handle_alert()
            ├── 节流: 距上次调用 < THROTTLE_S → sleep
            ├── inject_alert_analysis()
            │   └── POST nanobot /v1/chat/completions (180s timeout)
            │       prompt 包含: 告警上下文 + MCP 工具调用指令
            ├── 失败兜底: 静态中文告警消息
            └── push_to_gateway()
                └── POST gateway /api/internal/push (重试 3 次)
```

### 4.4 去重与节流

| 机制 | 参数 | 默认值 | 说明 |
|------|------|--------|------|
| 去重窗口 | `DEDUP_WINDOW_S` | 300s (5min) | 同一 `{greenhouse_id}:{sensor_type}` 在窗口内不重复触发 |
| 节流间隔 | `THROTTLE_S` | 2.0s | 连续两次 nanobot API 调用的最小间隔 |

### 4.5 AI 分析 Prompt 模板

- `session_id` 缺失时自动生成 `uuid.uuid4().hex`

- 消息前注入 `[System: 当前用户: {username} | 部门ID: {dept_id}]`
- 转发到 nanobot `/v1/chat/completions` (stream=true)
- 即使 nanobot 返回空内容，也会发送 `done: true, empty: true`

| Gateway | Backend | HTTP | `/iot/subscription/list` | JWT (Header) |

### 8.3 数据格式约定

**RuoYi AjaxResult 格式** (Java 后端响应):
```json

  "msg": "操作成功",
  "code": 200,
  "data": { ... }

```

**RuoYi TableDataInfo 格式** (分页响应):

## 9. 安全架构设计

### 9.1 认证层级

```
┌───────────────────────────────────────────────────┐
│                  认证架构                          │
│                                                   │
│  Layer 1: 用户认证 (Gateway)                      │
│    ├── JWT Token (HS512)                          │
│    ├── Redis login_tokens:{uuid} 验证             │
│    └── 无开发后门 (?user_id= 已移除)              │
│                                                   │
│  Layer 2: 服务间认证 (MQTT Bridge → Gateway)      │
│    ├── X-Internal-Secret Header                   │
│    └── 无 HTTP 暴露 (仅 Docker 内网)              │
│                                                   │
│  Layer 3: 参数安全 (MCP Server)                    │
│    ├── 6 层校验管道                               │
│    ├── Prompt Injection 检测 (8 模式)             │
│    ├── Token-Gated 写确认                         │
│    └── 物理范围校验                               │
└───────────────────────────────────────────────────┘
```

### 9.2 Prompt Injection 防护

**检测层**: validators.py Layer 2

**8 种检测模式**:

| 模式 | 目的 |
|------|------|
| `ignore (all) (the) (previous\|above\|...) instructions?` | 指令覆盖 |
| `forget ... instructions?` | 指令遗忘 |
| `you are now (a)? (different\|new)` | 角色替换 |
| `pretend (you are\|to be)` | 角色伪装 |
| `act as (if)? (you are\|a different)` | 角色切换 |
| `system_prompt:` | 系统提示注入 |
| `<\|im_start\|>` | ChatML 注入 |
| `<\|im_end\|>` | ChatML 注入 |

**处理**: 检测到 → `HardBlockError`（不可恢复），记录审计日志。

### 9.3 Token-Gated 写确认

**适用操作**: `resolve_alarm`, `close_alarm`, `mark_false_alarm`, `set_threshold`, `set_silence_config`, `subscribe_alarm`, `unsubscribe_alarm`, `generate_daily_report`, `generate_greenhouse_report`

**安全保证**:
- Token 随机生成 (hex, 16 字节)
- 单次使用（用后即废）
- 5 分钟有效期
- 内存存储（不持久化）
- LLM 无法预测或绕过

## 13. 错误处理与容错设计

### 13.1 Gateway 容错

| 场景 | 处理方式 | 影响 |
|------|---------|------|
| JWT 验证失败 | 返回 401 | 请求被拒绝 |
| nanobot 不可用 | httpx 超时, 发送 `done: true, empty: true` | 用户收到空响应 |
| Redis 不可用 | Auth → 401; JWT 存储 → 静默忽略 | 鉴权失败/MCP JWT 丢失 |
| WebSocket 断开 | 心跳清理, 推送静默失败 | 用户需重连 |
| 任务持久化失败 | 日志告警, 内存中仍有效 | 重启后任务丢失 |

### 13.2 MCP Server 容错

| 场景 | 处理方式 | 影响 |
|------|---------|------|
| 后端 API 超时 | httpx 30s 超时, 返回错误信息 | LLM 可看到错误并重试 |
| 参数校验失败 | `ValidationError` → LLM 可重试 | 工具返回错误提示 |
| 注入检测 | `HardBlockError` → 记录审计 | 操作被阻止 |
| Token 不匹配 | 返回确认提示 | LLM 需重新调用 |
| Neo4j 不可用 | 自动降级到文件模式 | 知识图谱功能降级 |
| Mock 模式 | `MockDongzaoClient` 替换 | 无需真实后端 |

### 13.3 MQTT Bridge 容错

| 场景 | 处理方式 | 影响 |
|------|---------|------|
| MQTT 连接断开 | paho 自动重连 | 短暂消息丢失 |
| JSON 解析失败 | 日志告警, 静默丢弃 | 单条消息丢失 |
| nanobot 分析失败 | 静态兜底消息 | 用户收到通用告警 |
| Gateway 推送失败 | 3 次重试 + 线性退避 | 最终失败则告警丢失 |
| 去重误杀 | 5 分钟窗口内同大棚+传感器 | 短时间重复告警被抑制 |
| 节流触发 | sleep 等待 | 告警分析延迟 |

### 13.4 兜底消息模板

当 nanobot 分析失败时，MQTT Bridge 使用以下静态消息：

```
🔴 {greenhouse_id} {sensor_type} {value}{unit} 触发 {status} 告警
自动分析暂时不可用，请手动查看。
```
